# Cross-Site Scripting (XSS)

По мере того как веб-приложения становятся все сложнее и сложнее, в то же время это ведет к увеличению количества уязвимостей. Среди наиболее распространенных типов уязвимостей веб-приложений почетное место занимает Cross-Site Scripting (XSS). Уязвимости XSS используют недостаток очистки пользовательского ввода, чтобы «записать» код JavaScript на страницу приложения и выполнить его на стороне клиента, что приводит к нескольким типам атак.

---

## **Что такое XSS**

Обычное веб-приложение работает, получая HTML-код от серверной части и отображая его в браузере на стороне клиента. Если уязвимое веб-приложение не выполняет должную очистку пользовательского ввода, злоумышленник может внедрить дополнительный JavaScript-код в поле ввода (например, комментарий/ответ). Когда другой пользователь открывает ту же страницу, он невольно выполняет этот вредоносный JavaScript-код.

Уязвимости XSS выполняются исключительно на стороне клиента и, следовательно, не оказывают прямого воздействия на серверную часть. Они могут затрагивать только пользователя, который выполняет вредоносный код. Прямое влияние уязвимостей XSS на серверную часть может быть относительно низким, но они довольно часто встречаются в веб-приложениях. Это соответствует среднему уровню риска (`низкое влияние + высокая вероятность = средний риск`), поэтому мы всегда должны стремиться `снизить` риск, выявляя, устраняя и проактивно предотвращая подобные уязвимости.

## **XSS Attacks**

Уязвимости XSS могут способствовать широкому спектру атак, которые могут представлять собой все, что может быть выполнено с помощью JavaScript-кода браузера. Основным примером XSS-атаки является то, что целевой пользователь невольно отправляет свой сессионный файл cookie на веб-сервер злоумышленника. Другим примером является выполнение браузером цели вызовов API, которые приводят к вредоносному действию, такому как смена пароля пользователя на пароль по выбору злоумышленника. Существует множество других типов XSS-атак, от майнинга биткоинов до показа рекламы.

XSS-атаки выполняют JavaScript-код непосредственно в браузере пользователя, что накладывает определенные ограничения. Этот код работает в рамках JavaScript-движка браузера (например, V8 в Chrome) и не может выполнять команды на уровне операционной системы. Также современные браузеры ограничивают выполнение кода доменом уязвимого веб-сайта.

Однако даже в таких условиях выполнение JavaScript в браузере пользователя может привести к серьезным последствиям, включая широкий спектр атак, описанных ранее. Более того, если исследователь обнаружит бинарную уязвимость в самом браузере (например, переполнение кучи в Chrome), то уязвимость XSS может быть использована для запуска эксплойта через JavaScript. В результате этот эксплойт может выйти за пределы изолированной среды браузера и выполнять вредоносный код уже на компьютере пользователя.

Уязвимости XSS встречаются практически во всех современных веб-приложениях и активно эксплуатируются уже более двух десятилетий. Один из самых известных случаев XSS — это червь [Samy Worm](https://en.wikipedia.org/wiki/Samy_\(computer_worm\)&#x29;, который использовал сохраненную XSS-уязвимость на сайте социальной сети MySpace в 2005 году. Червь запускался, когда пользователь просматривал зараженную страницу, куда злоумышленник добавлял сообщение: &#x5F;"Samy — мой герой"_. Это сообщение содержало JavaScript-код, который автоматически публиковал это же сообщение, но уже на странице жертвы, при просмотре ее профиля другими пользователями. За один день червь распространился на страницы более миллиона пользователей MySpace. Хотя в данном случае вредоносная нагрузка не нанесла серьезного ущерба, уязвимость могла быть использована для более опасных атак: кражи данных банковских карт, установки кейлоггеров в браузерах пользователей или даже эксплуатации бинарных уязвимостей в веб-браузерах, которые на тот момент встречались гораздо чаще.

В 2014 году исследователь в области безопасности случайно обнаружил [уязвимость XSS]() в панели управления TweetDeck в Twitter. Эта уязвимость была использована для создания твита с [самостоятельным ретвитом](https://twitter.com/derGeruhn/status/476764918763749376) в Twitter, в результате чего твит был ретвитирован более 38 000 раз менее чем за две минуты. В конце концов, это вынудило Twitter [временно отключить TweetDeck](https://www.theguardian.com/technology/2014/jun/11/twitter-tweetdeck-xss-flaw-users-vulnerable), пока они исправляли уязвимость.

To this day, even the most prominent web applications have XSS vulnerabilities that can be exploited. Even Google's search engine page had multiple XSS vulnerabilities in its search bar, the most recent of which was in 2019 when an XSS vulnerability was found in the XML library. Furthermore, the Apache Server, the most commonly used web server on the internet, once reported an XSS Vulnerability that was being actively exploited to steal user passwords of certain companies. All of this tells us that XSS vulnerabilities should be taken seriously, and a good amount of effort should be put towards detecting and preventing them.

По сей день даже самые известные веб-приложения имеют уязвимости XSS, которыми можно воспользоваться. Даже страница поисковой системы Google содержала множество уязвимостей XSS в строке поиска, самая последняя из которых была [обнаружена в 2019 году](https://www.acunetix.com/blog/web-security-zone/mutation-xss-in-google-search/), когда уязвимость XSS была обнаружена в библиотеке XML. Более того, сервер Apache, наиболее часто используемый веб-сервер в Интернете, однажды [сообщил об уязвимости XSS](https://blogs.apache.org/infra/entry/apache_org_04_09_2010), которая активно использовалась для кражи паролей пользователей определенных компаний. Все это говорит нам о том, что к уязвимостям XSS следует относиться серьезно и приложить немало усилий для их обнаружения и предотвращения.
